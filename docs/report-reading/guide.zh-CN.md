# 怎么读一份报告

每个工具都返回一份报告。它们共享同一副骨架，差别在**把发现放在哪里**。这份指南讲的是阅读
顺序：先看什么、每个字段回答什么问题、以及一份报告**不**告诉你什么。

这份指南的行文结构来自它旁边那张思维导图——它是**从活报告生成的**，不是手画的。手画的图会漂移；
这一张无法声称一个引擎并不产出的形状。

## 三个问题，按顺序

### 1. 跑起来了吗？

`ran` 能把「工具拒绝」与「工具跑过」分开，但它只回答了**一种**拒绝。边界上的拒绝——参数形态不对、
格式不存在、记号不是记号——回的是 `ran: false`、带 `errorCode`、`verdictReason` 以
「the tool did not run」开头。这时没有可路由的判定，去修调用。

**引擎自己的 schema 拒掉的输入是另一种形状**，而且更容易误读，因为它看起来像一次评审：
`ran: true`（引擎确实跑了）、`ok: false`、`verdict: fail`、**没有 `errorCode`**，只有一条发现挂在
id 为 `MODEL`、`DATA_MODEL` 或 `DESIGN` 的检查下，且 `summary.checksRun` 为 `0`。读作
「**问题在输入，不在设计**」——真正被评审过的模型一定检查过东西，所以 `checksRun` 非零才是
「模型有缺陷」与「模型写歪了」的分界。

所以拒绝与失败评审需要不同应对，而**光看 `ran` 分不开**：判据是 `ran: false`，或者 `checksRun: 0`
配一条以校验命名的检查。

### 2. 判了什么？

`verdict` 就是答案，取值有三个：

| `verdict` | 含义 |
|---|---|
| `pass` | 检查跑了，没有可报的东西 |
| `pass_with_findings` | 只有 warning；没有任何一项判定不利于这个模型 |
| `fail` | 至少有一条 error 级发现 |

**读 `verdict`，不要读 `ok`。** `ok` 在各族的含义不同——多数族在评审失败时仍是 `true`，组合族在
出现 error 级发现时是 `false`——所以它不能当判定读；把它当判定读，会得出与报告相反的结论。
`verdict: "fail"` 是一次**成功的运行发现了东西**，这正是本插件告诉你缺陷的正常方式。

`verdictReason` 是一句话的「为什么」，它点名第一条 error 码。当判定与你预期不符时，从这里开始。

### 3. 我该做什么？

`nextSteps` 永不为空，而且它是**从发现推导出来的**，不是写在旁边的。它指出报告没有覆盖的那部分该
走哪条路：另一个检查、一次源码侧扫描，或一个外部检查器。

## 每份报告共享的骨架

`ok`、`ran`、`verdict`、`verdictReason`、`schema`、`summary`、`nextSteps`——每一族都带全。`schema`
是版本化的契约，读者靠它知道自己手里是哪一种形状。

`hashes` 与 `modelHash` 的存在是为了让两份报告可以比较。**同样的输入加同样的哈希规格得到同样的
哈希**；哈希变了就意味着模型变了——这正是 diff 能有意义的前提。

`summary.boundNotes` 记下**被替换或被夹取**的预算，`metadataKeys` 列出 schema 当作注释忽略掉的
`_` 前缀键。两者都由渲染后的正文印出来（`BOUND`、`METADATA`），所以只拿到正文的读者也知道：
数字来自另一个界，而不是你要求的那个界；你写的某个字段被当成了注释。

报告在发现之外还可能带**注记**：`warnings` 装的是记号或解析器承载不了的东西。它们计进判定，所以
正文把它们印在 `WARNING` 下；当发现名册本身为空时，`FINDINGS` 那一行会说明有几条。正文一边说
「nothing was reported」、一边头顶的判定早就数过那条注记——那正是这行字修掉的缺陷。

## 发现放在哪里

这是各族的差异所在，先弄清它，再去找：

| 位置 | 族 |
|---|---|
| 在**各检查内部**，即 `checks[].findings` | `model_verify`、`model_compose_verify`、`model_datamodel_verify`、`model_design_review` |
| 在**顶层**，即 `findings` | `uml_structure_verify`、`uml` 的 review 路径、`model_concurrency_scan` |
| **哪里都没有**——比较 `added` / `changed` / `removed` | `report_diff` |

挂在检查下的发现归属于某个检查，而检查自己也带状态：`pass`、`fail` 或 `skip`。顶层发现没有检查
可归属，所以那些族改报一个 `summary`。

这个状态**故意是粗的**：`fail` 的意思是「这个检查有发现」，不是「发现很严重」。只含 warning 的检查
和含 error 的检查一样是 `fail`，所以**单看 `status` 判断不了判定有没有动**——那要看发现自己的
severity。**渲染出来的正文把两者分开了**，因为那是给人读的：正文里的 `fail` 表示至少一条 error，
`warn` 表示只有 warning。当正文把某个检查列在 `warn` 下、而 JSON 给同一个检查写
`"status": "fail"` 时，**两者都对**，它们回答的是不同的问题。

`summary.checksRun` 数的是**真正检查过模型的**那些，所以只要有跳过，它就小于检查对象总数。
`summary.checksSkipped` 点名被跳过的那些；一个都没跳过时这个字段不出现。

`report_diff` 还有第二处不同：它没有发现，因为它的对象是**另两份报告之间的差异**。`verdict` 描述
增量，`currentVerdict` 描述当前这次运行**自身**的判定。两者恰好在「运行不干净但增量为空」时分岔
——把一份失败报告与它自己比较，得到 `verdict: "pass", currentVerdict: "fail"`，而两句都成立：
什么都没有变，而这次运行是失败的。

增量看三样东西，而其中只有一样是「新」的：`added`、`removed`、`changed`——同一个身份、但变了。警告
升成 error 落在 `changed` 里而不是 `added` 里，**它照样让增量失败**：这一刀什么都没加，却让报告变差
了。反过来，error 降成警告也会被点名，但不使增量失败。

## 先读严重度，再读码

一条发现内部，严重度决定它是否改变了判定：

- **error** —— 就是它让判定成为 `fail`；
- **warning** —— 报出来，但不使增量失败；
- **info** —— 上下文，例如某个元素使一组发现不可分割；
- **undecided** —— 搜索在判定之前停下了。**不是通过。** `summary.truncated` 对整份报告说的
  是同一件事；此时渲染后的正文会以一行 `LIMIT` 开头，只拿到正文的读者在读到任何发现之前就会知道。

发现的码以**拥有它的检查**为前缀（`S1`、`A4`、`DS5`、`DA2`、`DES12`、`UML023`），所以一个码在你
读它的消息之前就告诉了你该去哪里看。

### 码是给你用的，不是给你回答的那个人用的

码存在的意义是让你把发现**路由**到解释它的参考资料，并让这次运行能和上一次比较。**没读过报告的
用户不知道 `A4_NO_RELEASE_EVENT` 是什么意思**，而一段背诵码的回复会让工作显得不透明，同时没告诉
对方任何能行动的东西。

**把发现说的话用文字说出来。** 每条发现自己的 `message` 本来就是**为不懂码的读者写的句子**——直接
用它。只有当码能帮用户在报告里找到同一行时才提它，并且**同时给出含义**：不是「S7 失败了」，而是
「不变式被违反——模型经过两个事件到达 C（`S7_INVARIANT_VIOLATION`）」。

同一条规则也适用于检查 id：`Event Completeness` 是**名字**，`S5` 是**标签**。以名字开头。

有一个码值得连**理由**一起转达，而不只是名字：可达状态空间无限的模型报 `S6_UNBOUNDED_VARIABLE`，
且是 error；要传达的重点是**任何**搜索上限都决定不了它——那个问题对这个模型是**不可判定**的，
而不只是「还没答」。

## 各族额外带了什么

骨架之外，每一族带着自己领域需要的东西：一张图、一份往返记录、一个记号、渲染出的源文本、那三个
增量列表，或者设计评审的 `violations` / `signals` / `facts` 三分。读 `schema` 就知道手里是哪一种，
再去读属于它的那一节。

设计评审的那三个列表值得弄清，因为**只有第一个判断任何东西**：

- `violations` —— 决定判定的检查级别。有十个码在这一级，从依赖环到解析不到的类型关系；
- `signals` —— 四个码，值得一看，但不使任何东西失败；
- `facts` —— 根本不是发现：**一个测量对象**，装着这张图的数字（`density`、`ranks`、
  `articulationPoints`、`feedbackArcs`、`largestCycle`）。它还带 `checksSkipped`，读者正是在这里
  得知有九项检查因为没有声明而从未运行。

没有任何码同时出现在 `violations` 和 `signals` 里：这个划分是互斥的，所以只读 `violations` 的
读者会看到**每一条决定了判定的发现，且不含任何没决定的**。

## 报告不告诉你什么

- **它讲的是模型，不是代码。** 一个干净的判定是关于**你提供的那张图**的证据。把它与源码对账是
  另一件事，而两者的差异通常正是发现所在。
- **被截断的搜索什么都没判定。** 当 `truncated` 为真时，提前停下的检查会把自己报成 undecided，
  而不是通过。
- **被跳过的检查什么都没看。** `skip` 与 `pass` 是两个不同的答案：没有可用词汇的检查没有看，
  而把这件事说出来正是要点。
