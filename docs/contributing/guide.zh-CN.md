# 参与贡献

这个仓库会收到两类来件，而它们需要你提供的东西不同。动笔之前先确定自己手里是哪一类——因为
维护者问的第一个问题，两类并不一样。

**用中文写完全没问题。** 两份 issue 模板都有中文版，而且**报告是按「能不能复现」来判的，不是按
英文水平**。本指南其余部分是英文，因为仓库是公开的；模板不是——**那是给你填的表格**。

这份指南的行文结构来自一张从本仓库生成的思维导图：[mindmap.mmd](mindmap.mmd)。它点名的入口都是
真实存在的，它引用的计数在 `docs/contributing/facts.json` 里。

English: [CONTRIBUTING.md](../../CONTRIBUTING.md)

## 你手里是哪一类？

**关于方法的断言。** 你有一个来源——一篇论文、一份规范、一个有文档的算法——它说某条检查应该
换个算法。或者你发现某个判定在**计算上**有缺陷。

**关于行为的断言。** 某个工具给出的答案你认为不对、拒绝了本该接受的输入、崩溃了，或者把进程
拖垮了。

如果两者都是，**先报行为**。行为谈清楚之后，方法提案才好评。

## 有出处的改进

### 要引用什么

- **已发表的方法**，带年份与出处，以及你在其中读到的段落。
- **它要取代的本仓库约定。** 有些检查是已发表方法，有些是本仓库自己的约定，参考文件把两者分开
  记录：目前 **10 个参考文件里有 4 个**带 provenance 段。多数检查是约定，所以一个假定自己有
  已发表基础的提案，必须说明它从哪来。
- **来源有没有被读对。** 同一个来源里的两个结果常常是邻居：feedback **arc** set 与 feedback
  **node** set 是两个问题，而你需要的是其中一个——本仓库的 provenance 表记下了它们取的是哪个
  （arc set 取 `Garey & Johnson 1979`，见设计评审的笔记与结构指南）。如果你的提案引用某来源，
  请把读到的原句贴出来；它该进参考文件的 provenance 段。

### 关于判定要说什么

- **改的是哪条检查，用它的码说。** 码声明分布在 **14 个源文件**里，最大的一组在数据引擎。点名
  码的提案，维护者才动得了手。
- **它改的是判定，还是新增一个信号。** 这是承重的区别：**只有 violation 级决定判定**。有用但
  不决定性的检查属于 signal 级——那里会被报出来，而不使任何东西失败。
- **用文字说明它不决定什么。** 这里的每条检查都在自己的范围声明旁边写出自己的非目标，新的检查
  也应当如此。

### 必须附带什么

- **最邻近的那个必须仍然通过的用例。** 一条「什么都能触发」的检查证明不了任何东西，所以最邻近
  的反例不是可选项：取那个**应当**触发发现的形式，然后把其中一个条件改对，要求它保持沉默。
- **一条能让新用例变红的变异。** 在**临时副本**里故意把引擎改坏，要求你的测试发现它。**不会
  失败的用例不是用例**——本仓库在这上面吃过亏：曾有一套测试断言「每个码**都能**出现」，而一个
  无条件报出所有码的引擎也能通过它。
- **权衡的另一面，如果存在的话。** 用运行时间换精确度、或用内存换完备性的方法，要在提案里说出来，
  而不是在评审里被发现。

## 运行中遇到的问题

### 要交什么

- **确切的那次调用，带参数。** 工具名与你发出的完整参数对象。如果涉及模型，说明是哪个，以及是否
  重复调用过。
- **你得到的东西**，**原样引用**而不是概括：
  - `verdict` 与 `verdictReason`——后者点名第一条 error 码；
  - 发现码，逐字；
  - `schema`，因为各族**阅读顺序不同**，把报告当成别的族来读会得出错误结论。
- **你期望是什么，以及为什么。** 那条规则、那个来源，或者说明答案本该不同的推理。

### 最值得先报的几种形态

- **一个读起来像「通过了」但什么都没查的判定。** **从未运行的检查不是通过的检查。** 本插件最主要的
  缺陷类别，一直是一个解析不到任何东西的名字——它把某条检查关掉，然后报出正面的全部通过。
- **本该返回报告却给出拒绝**，或者**抛出的裸错误没有可路由的码**。
- **进程死掉**，或者**搜索停不下来**。

### 什么让它可复现

- **能显示出问题的最小模型或图。** 一直删到「再删任何一处效果就消失」为止；那条边界通常就是报告。
- **你运行的版本**，以及你拿到手的 `schema`。
- **它是稳定复现还是偶发。** 报告按契约是**确定性的**——同样的输入加同样的哈希规格得到同样的
  哈希——所以「有时」本身就是一条值得写出来的发现。

## 两者都必须通过什么

CI 在 Node 20 与 Node 22 上跑这些：

1. `npm ci --legacy-peer-deps`
2. `npm run typecheck`
3. `npm run build`
4. `npm run test:engine` —— 回归链
5. `git diff --exit-code -- lib` —— 提交的构建产物必须与源码一致

`lib/` 是提交进仓库的，所以对 `src/` 的改动要在**同一个提交**里带动 `lib/`。

### 测试套件遵守的仓库规则

完整方法在 [tests/AGENTS.md](../../tests/AGENTS.md)。其中塑造「按码写用例」的几条：

- **一个用例只针对一个码。** 输入产生那个码，且旁边没有别的 error。
- **断言是哪条检查携带它**，这样码无法从兄弟检查漏进来而蒙混过关。
- **每个码都要有一个最邻近的反例**，那个输入必须**不**产生它。
- **从公开 API 不可达的码要钉住，而不是跳过**——断言遮住它的那个条件，这样条件一变用例就红。
- **不许有脆弱计数**，无论发布文本还是测试名。点名能力，别点数量。

### 必须随改动一起动的文档

- 该领域的参考文件——当某条检查或某个码变化时。
- [.github/memory](../../.github/memory/MEMORY.md) 下的记忆条目——当做出了一个决定时；根文件列出
  分类，每个分类有一个索引需要加行。
- 中英成对的那份要一起动：`README.md` 与 `README.en-US.md` 在同一个提交里改。

## 本地跑这些门禁

```bash
npm install
npm run typecheck
npm run build
npm run test:engine
npm run lint:md
```

`npm run test:full` runs the combined path. `npm run bump -- --check` 与 `npm run bump -- --audit` 校验所有清单
的版本一致；发版流程见 [RELEASE.md](../../RELEASE.md)。
